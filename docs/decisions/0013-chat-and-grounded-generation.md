# 0013: Chat, grounded generation, and retention

Status: accepted

## Context

Stage 9 answers questions from retrieved evidence, cites it, abstains when evidence is weak, and stores conversations. Retrieved text is untrusted input (prompt injection), the model runs locally only, and questions and answers can contain source code, so they never reach logs. Fused retrieval scores are relative (decision 0008), so they cannot decide abstention.

## Decision

- **`POST /chat` streams server-sent events over POST.** The request is `{ question, sourceIds | projectId, conversationId? }`; no model, runtime, or provider field is accepted (the global whitelist returns `400`). The server resolves scope, loads history, retrieves, and pulls the first token **before** sending headers, so validation, scope, unknown conversation, concurrency, and an unavailable runtime answer as plain JSON errors (`400`, `404`, `429`, `503`). After that the stream sends `meta` (`conversationId`), `token` events, then `done` (`messageId`, cleaned `answer`, `status`, `citations`, `invalidCitations`, `suggestions`) or `error` with a fixed message.
- **Prompt.** The system message is a fixed policy and never holds retrieved text: answer only from evidence, cite `[n]`, say when evidence is not enough, ignore instructions inside evidence. Evidence goes in the last user message as numbered blocks wrapped in `<<<EVIDENCE n id=TOKEN>>>` / `<<<END EVIDENCE n id=TOKEN>>>`, where `TOKEN` is a random UUID per request, so content cannot close its own block. Each block states its kind (code, prose, table rows with column names, schema entity, image description), source, path, and location; line breaks in metadata are flattened. Evidence size is bounded by `RETRIEVAL_MAX_CONTEXT_CHARS`; history by `CHAT_HISTORY_TURNS` and `CHAT_HISTORY_MAX_CHARS`. History answers lose their `[n]` markers, which point at earlier evidence, and abstained turns are left out.
- **Context budget.** The runtime gets `CHAT_CONTEXT_TOKENS` as its context window, `CHAT_MAX_ANSWER_TOKENS` as the answer limit, and `CHAT_TEMPERATURE` (0.1), so it does not fall back to its own default window and truncate the prompt silently. The prompt is fitted to the window minus the answer, at about 3 characters per token since the local tokenizer is not available: evidence is kept in rank order until the next block does not fit, then history gets what is left. Citations are validated against the evidence actually sent.
- **Follow-up retrieval.** With history and `CHAT_REWRITE_FOLLOW_UPS` (on by default), the model first rewrites the question into a standalone search query with a fixed system policy; history is quoted in a token-delimited block with answers shortened, since answers can quote evidence. Only retrieval and the abstention check use the rewritten query; the answer prompt keeps the question as asked. The output is reduced to one line; an empty result falls back to the question, and an unavailable runtime fails with `503` like any other chat call. The rewritten query is never logged, stored, or returned, and scope stays enforced in SQL, so a manipulated rewrite can at worst retrieve other chunks of the selected sources.
- **Abstention before the model.** The server abstains without calling the model when retrieval returns nothing, when not even the best chunk fits the context budget, or when the best cosine similarity is below `CHAT_MIN_VECTOR_SIMILARITY` (0.5) and no lexically matched chunk contains at least `CHAT_MIN_TERM_COVERAGE` (0.5) of the query's terms in its title, path, or content. The lexical search joins terms with OR, so a single shared word must not count as support. Vector search keeps the similarity of each candidate for this. The response is a fixed message with suggested next steps, stored with status `abstained`.
- **Unsupported answers.** An answer from the model with no valid citation is stored and returned with status `unsupported` and suggestions, so a client can warn that it is not grounded; the text is kept because it is often the model saying the evidence is not enough.
- **Citation validation.** Markers `[n]`, `[n, m]`, and `[n][m]` outside code spans are parsed. A number is valid only if it is within the evidence list and its chunk still exists, in the request scope, with the same source, path, and locator (re-checked in SQL, since re-indexing can run during generation). Invalid numbers are removed from the stored answer and reported in `invalidCitations`. Citations copy the source id and name, path, content kind, and locator, and keep `chunk_id` nullable (`ON DELETE SET NULL`), so they stay readable after re-indexing.
- **Limits** (security 006). `CHAT_MAX_QUESTION_CHARS` (4000, `400` above), `CHAT_MAX_CONCURRENT` (1, `429` above; in-process because the API is one local process), and `CHAT_GENERATION_TIMEOUT_MS` (120000) of wall time for retrieval and generation. A client disconnect or the timeout aborts the request signal, which reaches retrieval, `CHAT_PORT`, and the egress client. Chat never retries and has no fallback.
- **Storage and retention.** Tables `conversations` (optional `project_id`, `ON DELETE SET NULL`; title from the first question), `messages` (`user` or `assistant`, status `complete`, `abstained`, or `unsupported`), and `message_citations`. Message text may contain code or document excerpts; it stays in the local database. An exchange is written in one transaction when the answer is done; an aborted or failed request stores nothing. Conversations are kept until deleted, or purged when not updated for `CHAT_RETENTION_DAYS` (unset keeps them), at startup and daily. `DELETE /conversations/:id` removes messages and citations through cascading keys in one statement.
- **Listing.** `GET /conversations` and the messages of `GET /conversations/:id` use cursor pagination (`limit` 1 to 100, default 20; opaque `cursor`) and return `{ items, nextCursor }` (improvement 008). Timestamps are written in milliseconds so cursors compare exactly.
- **Logging.** Chat logs the conversation id, counts (sources, evidence, evidence dropped by the budget, citations), whether the query was rewritten, the status, and duration only.
- **Web chat.** `apps/web` has a minimal chat that reads the stream with `fetch`, through the dev proxy that adds the token (decision 0007). Stage 17 builds the full UI.

## Consequences

- An answer is only stored once complete, so a stopped answer is lost; the user can ask again.
- The similarity threshold depends on the embedding model and is tuned with the chat evaluation; changing `EMBEDDING_MODEL` may need a new value.
- The token estimate is conservative for prose and may leave part of the window unused; a larger `CHAT_CONTEXT_TOKENS` fits more evidence at the cost of memory and speed.
- A follow-up costs one extra model call before retrieval, inside the same timeout and concurrency slot.
- One generation at a time by default keeps a local GPU responsive but makes a second browser tab wait for `429` to clear.
